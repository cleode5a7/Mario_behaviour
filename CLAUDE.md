## Overview

**Mario Behaviour Analysis** — a reproducible pipeline for studying how players learn to complete scenes in a Mario video game task. The analysis detects learning-phase changepoints from per-scene completion-rate data (Bernoulli) and clusters behavioural traces — both within individual scenes and pooled across scenes sharing a design-pattern category — using Fréchet distance fed into HDBSCAN or k-means. Results are rendered both as matplotlib PNGs and as an interactive browser dashboard served from a static export.

Built on the [`invoke`](https://www.pyinvoke.org/) task runner. The `airoh` pip package provides reusable invoke tasks; this repo customizes them via `tasks.py` and `invoke.yaml`.

## Architecture

**Always read `tasks.py` first** before proposing or implementing any pipeline change — it is the authoritative source of what tasks exist, how they are wired, and what parameters they accept.

**Execution flow:** `invoke run` triggers the project's analysis pipeline via `pre=` dependencies declared in `tasks.py`, then records `output_data/PROVENANCE.json` in its body. The four permanent tasks — `fetch`, `run`, `verify`, `clean` — are always present; intermediate steps are project-specific.

- `invoke.yaml` — all path and data config (`output_data_dir`, `source_data_dir`, `notebooks_dir`, `datasets:` for datalad datasets, `files:` for plain assets), plus the `verify:` and provenance settings
- `tasks.py` — project-specific invoke tasks; imports reusable tasks from `airoh` (`airoh.utils`, `airoh.datalad`, `airoh.provenance`, `airoh.verify`)
- `analysis/` — pure Python analysis logic, called by tasks in `tasks.py`
- `web/` — source of the interactive dashboard (`index.html`, `app.js`, `style.css`); no build step, no dependencies. `invoke dashboard` copies these into `output_data/web/` and serves that directory
- `notebooks/` — Jupyter notebooks executed by `run_notebooks` via `airoh.utils.run_notebooks`; notebooks receive `OUTPUT_DATA_DIR` and `SOURCE_DATA_DIR` as environment variables
- `source_data/CONTENT.md` and `output_data/CONTENT.md` — authoritative docs for what each data folder contains; update these when data assets change, do not duplicate their content elsewhere

**Analysis vs. notebooks:** Heavy computation belongs in `analysis/` Python code, invoked by `run-{name}` tasks, which write results to `output_data/`. Notebooks are for visualization only — they read from `output_data/` and produce figures. This keeps notebooks fast and focused.

**Idempotent tasks:** Each `run-{name}` task must check whether its outputs already exist and skip execution if they do. This means `invoke run` can be called repeatedly during development of a later step — earlier steps are skipped automatically. To force a full rerun, call `invoke clean` first, then `invoke run`.

**Task naming conventions:**
- Fetch tasks are named `fetch-{name}`, one per data asset; the umbrella `fetch` calls them all and routes a `--{name}-source` flag to each.
- Analysis tasks are named `run-{name}` (e.g. `run-preprocessing`, `run-model`).
- Cleaning tasks mirror them: `clean-{name}` removes only the outputs of the corresponding step.
- The top-level `clean` task calls all `clean-{name}` tasks in sequence, and only ever touches `output_data/`. Source assets have their own mirrored `clean-{name}` tasks (`clean-mario-scenes`) plus an umbrella `clean-source`, kept separate because removing a source asset is a deliberate act — e.g. before re-pointing a stale symlink — not something a rerun should do implicitly.
- The top-level `run` task wires all steps together via `pre=` chains in `tasks.py`.

**Task parameters:** `run-{name}` tasks should expose chunk or subset parameters (e.g. a subject ID, a chunk index) so that individual pieces can be rerun in isolation. They should also support a `smoke` flag for a fast minimal run useful for testing the pipeline end-to-end without running the full analysis.

**Project-specific conventions:**
- **Changepoints chunk by subject**: `run-changepoints` accepts `--subjects` (comma-separated subject IDs, e.g. `01,02`) and `--smoke` (first subject only). It loads each subject's full chronological attempt sequence across all scenes. Also exposes `--beta` (ruptures penalty scale), `--n-bkps` (Dynp changepoint count; defaults to the subject's Phase-transition count), and `--rep-block-size` (repetitions per block for the level-repetition signal, default 10).
- **The unit matters more than the detector.** Detection runs on two units. Per **scene clip** the completion rate is ~92% — a ceiling, flat, and no detector segments it; this is why `phase_changepoints()` (reading the experimenters' annotations) was made the primary method and why `run-changepoints-by-category` went looking in `Duration` instead. Per **level repetition** (one `.bk2` playthrough, grouped via the `SourceBk2` field) the rate is 53–81% by subject, and PELT/Binseg recover the annotated discovery→practice boundary to within 0–14 repetitions for all five subjects. When a signal looks undetectable here, check the aggregation unit before reaching for a different algorithm.
- **Never bin by phase for detection.** `phase_thirds()` / `phase_thirds_cleared()` produce the Early/Mid/Late-per-phase summary the lab reports, stored under `repetitions.phase_thirds`. Their bins are cut *at* the phase boundary, so a detector run on them would be handed the transition it is meant to discover (and six points cannot be segmented regardless). Reporting only.
- **In discovery, time and difficulty are perfectly collinear — by design.** Each level is played once, as a block, in world order, so "later in discovery" *is* "harder world", and each chronological third of discovery contains a **different, disjoint** set of levels. Consequently **no across-third comparison within discovery is valid, adjusted or not** — the bins differ in what was played, not just when. Raw, the cleared rate falls (77% → 66% → 33% for sub-01): difficulty gradient, not un-learning. Adjusted, it does not go flat (session-wide level means leave discovery at ~−11 pp overall) and for some subjects appears to *rise* (sub-02: −21.9 → −2.8) — but that is a **floor effect**, verified: late-discovery levels are the hard ones with no headroom (sub-02's world-8 levels gain −2/−8/+2 pp discovery→practice while w3l2 gains +75), level practice-rate correlates r=0.45 with that gap, and early-discovery levels average +36 pp of headroom vs +13 pp late. Do not read a learning trend into discovery. **Practice is the phase that supports a time course**: every third contains all 22 levels, so level mix is constant and the rise is real (−2.0 → +5.5 → +10.9 pp for sub-01; all five subjects monotonic, ~5-12 pp below their level average in discovery vs ~2-6 pp above in practice).
- **`within_level` binning is not a time axis.** `phase_thirds_cleared(..., within_level=True)` splits each level's repetitions into thirds and pools them, which controls difficulty but scatters each bin across the whole session (chronological medians 110/113/116 out of 230). It measures improvement *with repetition at a level*, not improvement over time. Retained in the JSON as the only within-discovery learning measure the design permits — but never plot it on an axis labelled like time.
- **Adjusted for reporting, raw for detection.** `level_adjusted_series()` is the right *effect-size* signal but a worse *detector* input: the subtraction removes much of the mean shift ruptures keys on, moving the nearest breakpoint from within 0-14 repetitions of the annotated boundary out to 60-80 away. Detection stays on raw `cleared`.
- **Changepoints-by-category also chunk by subject**: `run-changepoints-by-category` accepts `--subjects`, `--smoke`, `--beta`, `--n-bkps`. For each subject it restricts the attempt sequence to scenes sharing each design-pattern category (reusing `load_scene_patterns`/`list_categories` from `analysis/clustering.py`) and runs the ruptures detector on **both** the `Duration` (time-to-complete) and completion signals — the pooled-completion signal is near-ceiling and flat, so `Duration` is the signal that actually reveals learning. Chunked by subject (not by category, unlike clustering) because changepoint cost is cheap and the subject's chronological order is the natural unit; one output file per subject holds all their categories.
- **Clustering chunks by scene**: `run-clustering` accepts `--scenes` (comma-separated scene IDs, e.g. `w1l1s0,w2l3s4`) and `--smoke` (first scene only). It defaults to `--method consensus` with `--min-cluster-size 5 --cluster-selection-epsilon 20`, and also takes `--bootstraps`, `--frac` and `--seed`. The consensus aggregation is controlled by `--consensus-cluster` (`ward`, default, or `hdbscan`), `--consensus-input` (`features`, default, or `distance`), `--consensus-linkage`, `--consensus-k-max`, `--consensus-tol` and `--consensus-min-cluster-size`.
- **Clustering is bagged; the ensemble makes the labels.** `method="consensus"` refits HDBSCAN on `bootstraps` random `frac` subsamples and builds a co-association matrix (`C[i,j]` = how often i and j clustered together *given both were drawn*); the labels come from cutting `C` (see the Ward bullet below). A cluster has to survive resampling to exist. `method="hdbscan"` is still there for a single fit, and `cluster_traces()` now returns `(labels, stability)` — the second element is `None` for the single-fit methods.
- **The ensemble is cut by Ward at a silhouette-chosen k, and `C` is handed to Ward as a *feature matrix*.** `ward_consensus_labels()` follows the BASC reference: `linkage(C, method="ward", metric="euclidean")` with the diagonal forced to 1.0, so each row is one trace's co-occurrence profile and Ward runs on Euclidean distances between profiles. This is not a stylistic choice. Ward's criterion is defined on squared Euclidean distances, and our input space is Fréchet — a metric, but not Euclidean-embeddable — so feeding `squareform(1 - C)` as a precomputed dissimilarity would apply the Lance-Williams update to something not guaranteed to be Euclidean. **The co-occurrence representation is the step that launders a non-Euclidean input into a Euclidean one**, because `C` is built from the *partitions*, not from the input geometry. `--consensus-input distance` does use `1 - C` directly (first-order, "how often did these two cluster together", vs. the profile form's second-order "how differently do they relate to everything else") and is kept so the choice stays checkable — both are established (Fred & Jain vs. Strehl & Ghosh's CSPA).
- **Selecting k: the plain silhouette argmax, with both guards shipped off.** Cut the Ward tree at every k from 2 to `--consensus-k-max`, score each on `1 - C`, take the highest; ties go to the smaller k. Silhouette is scored on `1 - C` rather than in Ward's own feature space so the two `--consensus-input` modes stay comparable (scoring in the feature space was tried and moved almost nothing, ARI >= 0.98 on 9/10). The Fréchet silhouette is recorded per candidate but **does not select** — it prefers coarser cuts, and coarser flatters `stable_share` for free. The whole silhouette-vs-k curve is stored as `stability.consensus.k_candidates`, so a cut can be second-guessed without re-running the ensemble; the dashboard's `k selection` view draws it.
- **The two guards on that rule are still there, off, and each has a measured failure behind it.** `--consensus-tol` (0.0) is a plateau tie-break — smallest k within `tol` of the best. `--consensus-min-cluster-size` (1) restricts candidates to cuts whose smallest cluster clears it. Turn them on to get the earlier behaviour (`--consensus-tol 0.01 --consensus-min-cluster-size 5`) and compare; nothing about the ensemble changes, only the cut. **`--consensus-min-cluster-size` is not `--min-cluster-size`.** The latter is an HDBSCAN density parameter for the replicate fits and is scaled by `frac` inside `resample_labels`; the former is an eligibility test on a full-data Ward cut, with nothing to scale. They were one flag until the rule was simplified, which is how a Ward cut came to be floored at a value swept for the density fits.
- **What the plain rule costs, measured over the corpus.** The bulk partition barely moves — **ARI 0.996 median** against the guarded rule, nothing below 0.5, 279/308 above 0.9 — but k rises in **172 of 300** scenes and never falls (median 5 -> 6, mean 7.45, mean delta +2.0). The extra clusters are mostly dust: the smallest cluster is **<= 2 traces in 126 scenes (42%) and exactly 1 in 95 (32%)**, where under the floor it could not be. Where k rose, the median silhouette gain bought was **0.0098** for a median k of 5 -> 9. Trace-weighted `stable_share` is essentially flat (79.7% -> 79.1%), and mean silhouette rises 0.809 -> 0.818 — which is what an argmax does by definition and is not evidence the partition improved. **The silhouette cannot see the problem**: sklearn scores a singleton at 0, and a trace that never co-clustered already scores ~0 inside its parent, so peeling it off is free and the curve cannot fall. Anything that flags dust has to come from outside the metric — `k_candidates[].min_size`, the hollow markers in the dashboard, the bottom-right panel of `figure_clustering_silhouette.png`.
- **With the floor off, the maximum is almost always interior — and that is what shows the floor had been doing the truncating.** Over the 300 scenes that produce a partition, **276 pick an interior optimum** and only **24 pick the largest candidate on offer**, all 24 of them scenes that reach the `k_max = 15` ceiling, where the cap *is* the binding constraint. Under the old floor of 5 the same corpus read 113 interior against 187 at the top of the range: those 187 were not curves still rising, they were candidate lists cut short. `figure_clustering_silhouette.png` plots all of this. The Fréchet silhouette peaks and falls more often on the same scenes, which is why it is recorded per candidate; it prefers coarser cuts, so switching selection to it is a real change, not a refinement.
- **Do not tighten the k rule on the strength of a few bad scenes.** Three scenes with large `stable_share` drops (w2l3s0 84% -> 15%) each had Ward picking k above the replicate mean, which looks exactly like the granularity mismatch documented for `consensus_epsilon = 0`. It is not: those scenes were *selected because* they dropped. Measured on an unbiased 50-scene sample (under the guarded rule, which is the comparison those alternatives were against), the plain rule beat every alternative tried — 84.1% at median k=6, against 83.4% for capping k at the replicate mean, 83.9% for mean+sd, and 83.5% for widening `tol` to 0.05. There is no systematic finer-than-the-ensemble bias here. Re-measure on a random sample before "fixing" it — and note the honest open question the corpus numbers above pose is the opposite one, whether `--consensus-min-cluster-size` should sit at 2 or 3 rather than 1, which nothing has swept.
- **Two edge cases, and they are different.** `-1` appears on a consensus run only in the second one. (1) **No cut clears the size floor** — the k=2 cut is taken and `selection: "fallback_k2"` recorded, rather than the scene being dropped. Unreachable at the shipped `--consensus-min-cluster-size 1`, and kept for runs that raise it. (2) **The ensemble carries no signal at all**: on 8 small scenes (n=3 to 36) every replicate called every point noise, so the off-diagonal co-association is *identically zero*, `1 - C` is all ones and the silhouette is exactly 0. Ward will happily carve that flat matrix into arbitrary blocks, inventing structure the resampling explicitly failed to find, so `ward_consensus_labels` detects it and returns all-noise with `selection: "no_ensemble_signal"` — what the hdbscan aggregation did for those scenes, and the honest answer. Do not "fix" them by lowering the floor. Otherwise Ward assigns every trace, so a consensus partition has no noise class and `noise_frac` is 0.
- **`CONSENSUS_EPSILON = 0.4` is now the hdbscan path only, and is the record of why that path was demoted.** `cluster_selection_epsilon` is in Fréchet units and belongs to the replicate fits; the old consensus fit ran HDBSCAN on `1 - C`, bounded in [0, 1]. Passing the Fréchet value (20) exceeds every distance and collapses the scene to one cluster — a real bug caught in testing. But passing 0 is the opposite failure and subtler: the fit then splits on tiny co-association differences and comes out *finer* than the ensemble it summarises (w8l3s5: k=7 against a replicate mean of 2.7), and the per-cluster Jaccard scores that granularity mismatch as instability — 8% stable where a plain single fit scored 100%. 0.4 is the swept value ("co-clustered in >60% of the replicates they shared"), a flat optimum at 0.3-0.4 over 42 scenes with 0.0 the worst row. Needing a hand-swept constant at all is why Ward replaced it. Reachable via `--consensus-cluster hdbscan`; recorded in `params` only on that path, so a cluster file says which aggregation made it.
- **Two deliberate deviations from the BASC reference**, both pre-existing and neither introduced by the Ward switch. (1) **We resample the objects, not the observations.** BASC resamples time points and keeps every region in every replicate, so its denominator is just `n_samp`; we subsample traces, because the analogue — resampling frames — would force an O(n²) Fréchet recompute per replicate. That is why `coassociation()` conditions on co-inclusion. (2) **Our replicates have no fixed k and do produce noise.** BASC's replicates are k-means at a fixed k, so the consensus step just reuses it; ours are HDBSCAN, so there is no k to carry forward — which is exactly the gap silhouette fills. Silhouette is not second-guessing a choice the reference made, it is supplying one the reference never had to.
- **Count parameters scale with the subsample; distance thresholds do not.** `bootstrap_labels()` multiplies `min_cluster_size`/`min_samples` by `frac` and leaves `epsilon` alone. Holding the counts fixed silently raises the density bar — measured full-data k of 45/14/7 came back as 35.2/6.8/3.8 fixed, and 42.6/13.7/6.5 scaled. Fixed counts measure sample size, not stability.
- **Both resampling schemes exist; subagging is the default.** `resample_labels(scheme=...)` takes `"subagging"` (default) or `"bootstrap"` (Breiman: n draws with replacement). `run-scheme-comparison` runs the whole corpus under each at identical parameters/B/seed and writes `output_data/stability/scheme_comparison.json`. Result over 308 scenes (re-measured under the Ward aggregation and the plain k rule): the two **agree on the partition** (median ARI 0.966, 216/308 above 0.9) but disagree on the confidence — bootstrap's replicates are ~2x as variable (mean k sd 1.10 vs 0.61) and it reports trace-weighted 70.6% stable against subagging's 79.1%, with 93 scenes below 60% against 48. (Under the older hdbscan aggregation the same comparison read 73.9% vs 81.6%; the gap, not the level, is the point.) Use `--scheme bootstrap` when someone specifically wants classical bagging; the clusters will be much the same.
- **The aggregation is compared the same way the scheme is, and the Ward switch was not free.** `run-consensus-comparison` scores every scene under all three — Ward/features, Ward/distance, hdbscan-on-`1 - C` — and writes `output_data/stability/consensus_comparison.json`. Measured over 308 scenes on identical ensembles, under the plain k rule: **Ward/features 79.1% trace-weighted stable at median k=6, Ward/distance 80.5% at k=7, hdbscan 81.6% at k=4**, with the three agreeing closely on the partitions themselves (median ARI 0.94-0.99). So the default costs ~2.5 pp of `stable_share` against the old aggregation and buys +2 median k, plus a partition for the 11 scenes hdbscan left entirely as noise (Ward leaves 8, the ones whose ensemble carries no signal at all). That is the trade the project's own `select_params` rule already prefers (largest k above a floor, never the highest share, because coarser scores higher for free) — but it *is* a trade, not a free win, and the earlier 10-scene probe that suggested parity was too small. Do not re-quote that probe. **The ensemble is built once per scene and shared** across the three, because the replicate fits are the expensive part (~5 s a scene) and are identical for all of them; refitting per aggregation would triple the cost and leave room for a confounded comparison. `clean-stability` removes the file with the rest of `stability/`, so it needs no `clean-` task of its own.
- **`_one_replicate` always returns deduplicated indices**, which matters only under `bootstrap`: a point drawn three times contributes three identical rows to the fit, but the replicate partitions the *distinct* points it holds. Passing the duplicates downstream would make `coassociation` increment a pair once per copy and destroy the "replicates this pair was drawn into together" denominator. Deduplicating there keeps every downstream function scheme-agnostic.
- **Parallelise over scenes, not replicates.** One scene is ~4-5 s of work; one replicate fit is ~0.02 s, where joblib's per-task overhead exceeds the fit — measured, replicate-level `n_jobs=10` made subagging *slower* (6.0 s vs 4.0 s single-threaded). `run-scheme-comparison` parallelises over scenes and does 308 scenes x 2 schemes x B=200 in 1.9 min on 12 cores. Replicate-level `n_jobs` is still there and does help for the big per-category matrices, where a single fit is expensive. Draws are generated up front from one seeded rng, so parallelism never changes the answer.
- **Why subagging is the default — and it is not the duplicate-points story.** `resample_labels()` draws `frac*n` points *without* replacement, not `n` *with*. Measured over 35 scenes: a bootstrap replicate holds only ~63% unique points, so HDBSCAN fragments it and k comes out **1.29x** the full-data fit in 33 of 35 scenes (replicate sd 1.23); subagging gives 1.04x (sd 0.71). That bias is not cosmetic — the Jaccard scores the consensus partition against the replicate partitions, so replicates carrying 29% more clusters by construction depress it through mismatch rather than through real instability, the same failure mode as the consensus-epsilon note above. The often-cited duplicate-points-at-distance-0 effect is real but minor here (~0.2 pp more zero-distance pairs; the data already contains identical traces).
- **Parameters are recorded now, and were not before.** Every cluster file carries a `params` block. An audit of all 308 scenes recovered **14 distinct settings** in the old corpus — the dominant one (`mcs=10, min_samples=5, eps=0`, 144 scenes) was not even the `tasks.py` default. `analysis.stability.recover_params()` reconstructs settings for any file predating `params`, by grid search against its stored labels; all 308 recovered at ARI ≥ 0.999.
- **Stability tasks are per-scene and read only `output_data/`**: `run-cluster-audit` (establish each partition's parameters, then score it *at those* parameters — scoring with any other settings depresses the Jaccard through mismatch rather than real instability; a file carrying its own consensus `params` reports what it recorded and is never grid-searched, because a consensus partition has no single-fit equivalent and recovering one anyway reported 23% for a partition its own run measured at 96%). `audit.json` accumulates and skips scenes already present, so it stays a record of the corpus as it was — delete it to re-audit what is on disk now, `run-cluster-sweep` (`--scenes`, `--smoke`, `--min-cluster-sizes`, `--epsilons`, `--bootstraps`, `--frac`), and `select-cluster-params` (`--floor`). None of them opens `mario.scenes`; they use the cached Fréchet matrices, which is what makes a 12-point sweep over 308 scenes take minutes.
- **`stable_share` is the headline metric, and it is deliberately gameable-aware.** It is the share of a scene's traces in a cluster whose mean bootstrap Jaccard exceeds 0.75 — per-trace, so noise counts against it for free. But collapsing a scene to k=2 scores 93% on `w8l2s0`, so `select_params()` takes the **largest k above a floor** rather than the highest share. Never swap it for a plain argmax.
- **A global epsilon is in absolute Fréchet units — check `eps_quantile` before trusting it.** The sweep records where each epsilon falls in that scene's own distance distribution. At the selected `eps=20` the median is the 6th percentile and only 5 of 288 scenes put it above their median distance, so a single global value is defensible here. If source data changes, re-check before assuming it still is.
- **HDBSCAN's `cluster_persistence_` is useless on these matrices** — it returns all-`1.0`. Resampling is the only route to a stability number here; do not reach for the built-in.
- **Clustering-by-category still uses a single fit, deliberately.** `run-clustering-by-category` defaults to `--method hdbscan`, not `consensus`: a category pools up to ~19,000 traces where the matrix alone is ~2.9 GB and each subsample copy ~1.9 GB, so bagging there needs float32, a lower `B`, and the Jaccard-only path with no co-association matrix. The Ward consensus step adds an O(n²) linkage on top of that — the same warning, not a new one. `--method consensus` is available and correct for small categories. Do not "make it consistent" with the per-scene task without building that memory path first.
- **Clustering-by-category chunks by category**: `run-clustering-by-category` accepts `--categories` (comma-separated pattern tags, e.g. `"2-Horde,Flagpole"`) and `--smoke` (first category only). It pools traces from every scene sharing a tag, re-based to a common origin (each trace shifted to start at (0,0)) before computing Fréchet distance — otherwise distance would be dominated by each scene's absolute level position rather than trace shape. Cost scales with the *square* of the pooled trace count, which varies enormously by category (e.g. "Enemy" pools ~19,000 traces across 90 scenes vs. ~150 for the smallest category) — see `slurm_clustering_by_category.sh` for a SLURM array template and size resources per-category accordingly.
- Source data lives in `source_data/mario.scenes/` (a datalad dataset, git-ignored). `invoke fetch-mario-scenes` clones it, checks out `dev_refactor`, runs `datalad get`, and decompresses archives via the dataset's own `source_data/mario.scenes/code/archives/decompress.py` — or, given `--source`, symlinks an existing checkout and does none of those (see **Fetching data** above).
- `source_data/scenes_mastersheet.csv` (checked into Git, from Zenodo record 15586709) tags each scene with one or more design-pattern categories (28 binary columns, not mutually exclusive) — see `source_data/CONTENT.md`.
- Changepoint inputs: all `*_summary.json` files under `sub-{subject}/`, sorted by (Session, Run, StartFrame). Key field: `Outcome` (`"completed"` or `"death"`) → Bernoulli series.
- Clustering inputs: all `*_variables.json` files for a given scene (or, for clustering-by-category, for every scene tagged with that category). Trajectory built from `player_x_posHi × 256 + player_x_posLo` and `player_y_pos`.
- `analysis/changepoints.py` — changepoint detection on per-subject attempt series. `phase_changepoints(records, key=...)` (primary) reads the experimenters' `Phase` annotations — `key` selects the field so it serves both raw summary records (`"Phase"`) and repetition records (`"phase"`), returning indices in whichever unit it was given. `rep_attempt_series()` collapses scene clips into one record per level repetition keyed on `SourceBk2`, yielding two nested criteria: `cleared` (reached the level's end, deaths allowed) and `flawless` (no death at all) — this is the aggregation that lifts the completion signal off its ceiling. `bocd_pcp_curve()` is an offline **Bayesian** (BetaBinomial) diagnostic; `ruptures_changepoints()` wraps the generic `_ruptures_detect()`, a **non-Bayesian** detector running `ruptures` PELT/Binseg/Dynp with a **CostL2** mean-shift model on both the raw series and a block-averaged series (PELT/Binseg in penalty mode with an adaptive per-signal penalty `beta*log(n)*var`, `jump=1` for full resolution; Dynp in fixed-`n_bkps` mode). `_ruptures_detect` takes any 1-D signal, so it serves both the per-subject completion diagnostic and the per-category `Duration`+completion analysis. `category_attempt_series()` splits a subject's records by design-pattern category (a scene with multiple tags lands in each). All breakpoints are returned in **attempt-index space**.
- `analysis/stability.py` — resampling-based cluster stability. Everything in it takes a **precomputed distance matrix**, never traces, so it serves per-scene and per-category alike and never reads `mario.scenes`. `bootstrap_labels()` (scaled counts, fixed epsilon, no replacement), `jaccard_stability()` (Hennig 2007, restricted to in-sample members so the undrawn 20% is not scored as a failure), `coassociation()`, `ward_consensus_labels()` (the default aggregation: Ward on `C` as a feature matrix, k by the plain silhouette argmax — returns `(labels, report)` where the report carries the whole silhouette-vs-k curve, so a cut can be second-guessed without a re-run), `consensus_labels()` (the demoted hdbscan aggregation; zero diagonal forced — a trace called noise in every replicate would otherwise sit at distance 1 from itself), `trace_confidence()`, `sweep()`, `select_params()` and `recover_params()`. Also the file-reading drivers `run_cluster_audit()`, `run_sweep()`, `select_global_params()`, `run_scheme_comparison()` and `run_consensus_comparison()`.
- `analysis/clustering.py` — pairwise Fréchet distance matrix → bagged/single HDBSCAN or k-medoids, shared by `run_clustering` (per scene) and `run_clustering_by_category` (per scene category) via `cluster_traces()`. See TODOs in file. `load_traces(scene_id, source_dir, y_mode=...)` builds trajectories; `y_mode="raw"` (default) is what clustering distances/labels are computed on — **do not change the default**, existing results depend on it. Traces are ordered by a **unique** key `(Subject, Session, Run, StartFrame, ClipCode)` — `(Subject, Session, Run)` alone is not unique (a scene has many clips per run), so a weaker key would leave ties broken by non-reproducible filesystem order and misalign the positionally-stored labels. `y_mode="screen"` is a plotting-only vertical coordinate (`player_y_pos + 24 - (1 - player_y_screen)*256`, masked where `player_state == 0`) that stacks the two vertical NES screens into one continuous axis and hides dead frames; trace discovery/order is identical across modes so cluster labels still map 1:1.
- `analysis/trace_plots.py` — trajectory-figure rendering (pure visualization), imported by `notebooks/figure_clustering.ipynb`. `load_labeled_traces()` re-joins stored cluster labels to freshly-loaded traces **by clip key** (via `CLIP_KEY_FIELDS`), never by position, so plots stay correct even if the load order differs from when clustering ran (e.g. cluster-computed on SLURM, plotted locally). `load_labeled_traces()` returns `(traces, metadata, labels, method, stability)` — the per-trace confidence joins by the **same clip key** as the labels, never by position, and is `None` for runs that recorded none. `plot_scene_clusters()` draws one scene's traces (screen-corrected y), coloring by cluster (`color_by="cluster"`, default), by outcome (`color_by="outcome"`; green = completed, red = death), or by consensus confidence (`color_by="stability"`; magma ramp, painted low-confidence-last so the mush is what you see — the opposite of the attempt ramp's ordering, deliberately). If a `<scene_id>.png` background exists under `background_dir` (default `source_data/mario.scenes/sourcedata/scene_backgrounds/`) it is drawn with `imshow`, the y-axis is flipped in image space, and x is offset by the scene's mastersheet `Entry point`; otherwise it falls back to a plain data axis whose vertical range is clipped to the playfield via `playfield_ylim()` (percentile + few-screens cap) — a pit death is a *real* multi-screen downward fall in the screen-corrected coordinate, and clipping lets those honest-but-huge plunges run off the bottom edge instead of dominating the axis. `plot_scene_cluster_panels()` renders the same scene as one-subplot-per-cluster small multiples (shared axes) in a single figure, so individual cluster shapes are easy to compare. Background images are **not** in the dataset and must be regenerated (see `source_data/mario.scenes/code/deprecated/make_images/make_scene_img.py` — needs `stable_retro` + the source `mario` `.bk2` dataset); the deferred overlay lights up automatically once the PNGs exist.
- **Dashboard export chunks by scene**: `run-web-export` accepts `--scenes`, `--smoke`, `--step` (frame decimation, default 3), `--force` and `--backfill`. It exports only scenes that already have a `<scene>_clusters.json`, so it depends on `run-clustering` — unlike the other run tasks it is **not** independent. `invoke dashboard` serves the result. The payload's `cons` block is the k-selection record lifted out of the cluster file (`selection_report()`), which is what the dashboard's `k selection` view draws.
- **`--backfill` is for fields the payload can already derive.** `a` and `st` (below) come from `s`/`ph`/`clip`, which every exported record already carries, so `backfill_derived()` adds them to all 308 payloads in ~5 s without opening `mario.scenes`; a `--force` re-export would re-read tens of GB for the same result. When you add a payload field, ask whether it is derivable from what is already exported — if it is, extend `add_derived()` and the migration is a backfill, not a re-export.
- **Export once, serve statically.** The dashboard must never read `source_data/mario.scenes/` at runtime (it is 23 GB and usually a symlink outside the repo). `analysis/webexport.py` bakes the trace geometry *and* copies the background PNGs into `output_data/web/data/`, which is the only tree the browser sees. Anything the dashboard needs must go through the export.
- **The dashboard is a view, never a re-analysis.** Its subject/phase/stage/outcome filters change only which traces are drawn. Cluster labels come from the consensus run over all of a scene's traces, and the colour slot for each cluster is fixed by the **whole-scene** rank-by-size order — never the filtered order — so narrowing to one subject cannot repaint the clusters that survive. Only the `n=` counts and composition percentages recompute; the header then reads "N of M traces shown". If a future change makes a filter alter cluster identity, that is a bug, not a feature.
- **The exported payload is for drawing, not for numbers.** `run-web-export` keeps every `step`-th frame (default 3) and rounds coordinates to integers. Correct at 224 px tall, wrong for any measurement — quantitative work goes back through `load_traces()`.
- `analysis/webexport.py` — bakes the clustering results into the static payload the dashboard reads. `export_scene()` pulls geometry and labels through `load_labeled_traces()` (so the join stays by clip key, and the y coordinate stays screen-corrected), applies the mastersheet `Entry point` offset **to the exported coordinates themselves** when a background exists — so `x`, `xlim` and `bg_size` all live in one space and the browser does no arithmetic — decimates by `step`, and writes masked frames as `null` so the renderer breaks the polyline instead of interpolating across dead frames. `add_derived()` attaches `a` (attempt index) and `st` (phase tertile) from `analysis/stages.py`, and is shared with `backfill_derived()` so both paths use one definition. Per-trace stability is exported as `sb` and is **not** in `add_derived()` — it cannot be derived from the payload, so adding it is a re-export, not a backfill. `selection_report()` lifts the k-selection record — the `params` block plus the `stability.consensus` report, silhouette-vs-k curve included — into the payload as `cons`, so the dashboard can show how k was chosen without the browser seeing a cluster file; it is a few hundred bytes a scene and `None` for a single-fit run. `leaf_order()` re-expresses the dendrogram leaf order in **payload** indices (by clip key, like everything else here) and rebuilds the tree from the stored co-association matrix for cluster files written before `leaves` was recorded — `_consensus_tree` is a pure function of `C` and the two settings the file records, so that reconstruction is the same tree, not an approximation. `backfill_selection()` refreshes just the `cons` block in existing payloads: `cons` is not derivable from the payload (so it is not in `add_derived`) but *is* derivable from `output_data/` alone, which makes a change to the selection record a rewrite of 300 small JSON files rather than a `--force` re-export that re-reads tens of GB to reproduce identical geometry. `--backfill` runs it alongside `backfill_derived()`. `write_index()` rebuilds `index.json` from the exported files on every run so the index cannot drift, and carries `sil`/`sel` per scene so the picker can show the chosen cut's silhouette without opening a payload; `sync_backgrounds()` copies the scene PNGs in.
- `analysis/stages.py` — the two time-derived per-clip quantities the summary records do not carry, both keyed on `ClipCode` (`session‖run‖bk2-ordinal‖start-frame`, hence monotone in time within a subject). `attempt_index()` numbers each subject's entries into a scene 1..n chronologically; `stage_tertiles()` cuts each `(Subject, Phase)` group at the 1/3 and 2/3 `ClipCode` quantiles into `"e"`/`"m"`/`"l"`, a port of `add_stage_column` from the sibling `mario_learning.behavior` repo. Order is re-derived inside both functions rather than taken from list order, so they are safe to run over an already-exported payload.
- **Attempt index, not `rep-NNN`.** The repetition number in `SourceBk2` **restarts at zero every session** (sub-01 plays w1l1 as rep 0→10 in ses-001, then 0,1,2 again in ses-007, 0,1 in ses-008), so it is not a time axis and a viridis ramp keyed on it resets to dark ~15 times per subject. It also collapses re-entries: one `.bk2` yields several clips of a scene when the player dies and respawns into it. The attempt index counts each entry, which is the unit the trajectory plot draws. Do not "simplify" it back to the filename field.
- **Phase thirds are legitimate *here* — a scene is one level.** `stage_tertiles()` bins within `(Subject, Phase)`, and because a scene sits inside exactly one level the level mix is constant across the three bins. This is the `within_level=True` case, not the confounded chronological-thirds binning that the "Never bin by phase for detection" and "time and difficulty are perfectly collinear" notes above warn about — those concern discovery thirds taken across a whole session, where each third holds a *different* set of levels. Early/middle/late discovery on a single scene is a genuine repetition axis. Do not remove this feature on the strength of those warnings.
- **The matrix view offers two row orders, and they answer different questions.** `leaves` (the default) is the dendrogram order Ward itself produced, shipped as `cons.leaves` in payload indices. Cut clusters are contiguous in it — `cut_tree` cannot split a leaf run, verified on the corpus — so blocks still line up, but rows *inside* a block follow the merge structure, which is the only way to see that a cluster is really two things. `cluster` is the older rank-by-size order, where a block's internal order is payload order (subject, then time) and any sub-structure is scrambled; it is kept because the blocks then appear in the same order as the legend and the panels. Both are **whole-scene** orders that filters subset and never recompute, so narrowing to one subject cannot reshuffle what you are looking at.
- **The partition panel is derived in the browser, and is a picture of the labels, not a second measurement.** `renderPartition()` paints `adj[i,j] = 1 where label i == label j` — `part2adj` in the BASC reference — in the same row order as the matrix beside it, coloured by each cluster's legend slot rather than flat binary so a block can be matched to its trajectories. Nothing about it is exported: it is recoverable from `c` on every trace. The pairing is the point — left is what Ward was handed, right is what it returned, so a block solid on the right and mottled on the left is a cluster the cut asserted over weak agreement.
- **The co-association matrix is stored, not recomputed at view time.** `cluster_traces` drops it after deriving labels; `run-coassociation` regenerates it from the cached Fréchet matrix plus each file's recorded `params` (seeded draws, so exact — ARI 1.000 re-deriving the labels) into `output_data/coassociation/<scene>.npy` as uint16. **uint16, not uint8**: at uint8 the ~0.002 rounding shifts enough borderline mutual-reachability distances to change the partition (ARI 0.998). The web copy *is* uint8, because it is only painted — the same "payload is for drawing, not for numbers" split as the decimated coordinates. `export_coassociation()` permutes rows into payload order **by clip key** and skips the scene rather than exporting a silently transposed matrix if the keys do not line up.
- `web/app.js` — the dashboard renderer. The `matrix` view fetches `data/coassoc/<scene>.bin` lazily (only when opened) and blits one image pixel per cell with `image-rendering: pixelated` — a co-association cell is a datum, and smoothing would invent agreement values that were never measured. Hit-testing there is index arithmetic on the canvas, never a colour read back. The `selection` view draws `cons.k_candidates` — silhouette against k, the chosen cut ringed, the Fréchet silhouette dashed beside it as the recorded-but-not-selecting series, and any cut whose smallest cluster is <= 2 traces drawn **hollow**, because that marker is the only thing in the figure that can flag dust: the silhouette scores a singleton at 0 and a never-co-clustered point already scored ~0 inside its parent, so peeling it off is free and the metric cannot object. Like every other view it only draws a stored result — the selection happened in `ward_consensus_labels`, not in the browser. `Color by` offers cluster / outcome / subject / attempt / stage / stability; the stability ramp is `STABILITY_STOPS` (magma), deliberately not viridis, which already means "attempt #" — two sequential encodings sharing a palette is how a reader confuses them. Unlike the attempt ramp it needs no per-subject normalisation: `sb` is an absolute 0-1 confidence, comparable across scenes. the attempt ramp is normalised **per subject** (each player's own first attempt is dark, own last is bright) because players make very different numbers of attempts at the same scene, and a scene-wide denominator would make colour encode volume as well as timing. Palettes and the alpha/linewidth pairs are copied **verbatim** from `analysis/trace_plots.py`; if you change them there, change them here or the dashboard and the PNGs stop being the same figure. `sceneRanking()` (whole-scene, fixed colours) is deliberately separate from `visibleCounts()` (filtered, live labels). Hit-testing is a geometric nearest-point search in screen space rather than a colour picking-buffer, so an antialiased pixel can never decode to the wrong trace.
- `run-changepoints`, `run-changepoints-by-category`, `run-clustering`, and `run-clustering-by-category` are **independent** — they can be run in any order or in isolation. `run-web-export` runs after clustering, and so do the stability tasks (`run-cluster-audit` needs stored labels; `run-cluster-sweep` needs the cached Fréchet matrices). `run-clustering` keeps its selected defaults as literals rather than reading `selected_params.json`, so it stays runnable without the sweep having been run.

### Fetching data — clone, or point at an existing copy

Each data asset gets its own `fetch-{name}` task; the umbrella `fetch` calls them all and exposes a per-asset `--{name}-source` flag it routes to the matching one. `--source` is a single path bound to the single asset named in the call — never a root directory joined with each asset's filename — which is why there is deliberately no one shared `--source` for everything.

`mario.scenes` is a real datalad dataset, so it goes through `airoh.datalad` (`install_dataset` + `get_data`), configured under `datasets:` in `invoke.yaml`, rather than `airoh.acquisition.fetch_data`, which only symlinks or downloads a plain file. `scenes_mastersheet.csv` is checked into Git and has **no** fetch task; it is declared under `files:` with no `url` purely so `record_sources` puts its checksum in the manifest.

**A symlinked checkout is read as found.** `--source` links `source_data/mario.scenes` at an existing checkout and stops there: no `git checkout dev_refactor`, no `datalad get`, no `source_data/mario.scenes/code/archives/decompress.py`. All three write into a dataset this project does not own, and silently switching a colleague's branch is worse than reporting that the checkout is not ready. `fetch-mario-scenes` says so and stops when the linked tree has no JSON files. For the same reason `clean-mario-scenes` unlinks a symlink rather than following it — pointing at a shared 23 GB checkout must never put it one `clean-source` away from deletion.

**Gathering assets is a separate job from reproducing results.** `fetch` retrieves; `run` reads what is already on disk and never pulls. A `run` that quietly re-fetches hides the fact that a result came from data that arrived halfway through. If a step finds its input missing it should say so and point at `invoke fetch` — which is what every `run-*` task here does when `list_subjects`/`list_scenes` comes back empty.

### Recording asset versions

`fetch` writes `source_data/MANIFEST.json` and `run` writes `output_data/PROVENANCE.json` (see `airoh.provenance`). Between them they record what each input actually resolved to — including the commit, branch and dirty flag of a symlinked external checkout — and what produced the current outputs: the project's own commit, the environment, the manifest consumed, and a checksum per output file. Both are small and git-tracked.

`PROVENANCE.json` changes on every run. That is the record working, not churn to suppress; do not try to make it stable.

**These records attest, they do not retrieve.** They can say a result came from commit `abc123` of an input dataset with an uncommitted working tree — exactly what "why do my numbers differ from yours" needs — but they cannot bring that state back. That remains datalad's job. Because this project's dataset is usually a symlink to a checkout outside the repo, the manifest is the only thing that pins which commit of it the results came from.

### Verification

`invoke verify` (`airoh.verify`) checks that the code, config, data and documentation still agree: the task list against README/CLAUDE, `pyproject.toml` against `requirements.txt`, every path named in the docs, each data folder against its `CONTENT.md`, config keys against `tasks.py`, tracked file sizes, provenance freshness, and the linter. It exits non-zero on any FAIL. Configure it under `verify:` in `invoke.yaml`.

Run it before committing, and after any structural change — it catches the mechanical half of the "keep CLAUDE.md and README.md current" instruction below (renamed tasks, moved paths, undocumented outputs) that is otherwise left to memory.

It is deliberately **not** part of `run`: reproducing results must not depend on documentation hygiene, and a pipeline that refuses to compute because a README path moved is a pipeline people route around.

Two things this project configures under `verify:`, both deliberate: `ignore_paths` exempts `*<*`, because the docs name per-scene and per-subject outputs as patterns (`<scene_id>_clusters.json`) that no single file could satisfy; and it exempts the scene backgrounds, which are not in the dataset at all and only appear once someone regenerates them.

The checks are mechanical, so they cannot evaluate a claim like "this step never pulls data" or "the default step is 3". The `/verify` skill covers that second layer — it runs these checks, then reads the prose against the code. Use it after any change that alters what a step does, as opposed to what it is called.

**Testing:** two baseline checks, covering different failures. `invoke run-smoke` is the behavioural one — does the pipeline run end to end and produce something. `invoke verify` is the structural one — do the code, config, data and docs still describe the same project. Run both before committing; neither substitutes for the other.

**Adding a new analysis step:** add a function to `analysis/`, add a `run-{name}` task and a matching `clean-{name}` task in `tasks.py`, wire both into the top-level `run` and `clean` tasks via `pre=` chains, and create or extend a notebook in `notebooks/` for visualization.

**Evolving CLAUDE.md:** Run `invoke verify` after any structural change — it catches the mechanical half of this instruction. Keep this file current as the project grows. It should always reflect the actual scope of the project — what it does, what data it uses, and what analysis steps it contains. When adding or removing a task, rename a folder, or change the pipeline structure, update CLAUDE.md in the same commit. Stale guidance here misleads future AI sessions and collaborators alike.

**Keeping README.md current:** README.md is the user-facing documentation for this project. Any structural or workflow change — new tasks, renamed folders, updated commands, new dependencies — must be reflected there in the same commit. The task list in README.md should match `invoke --list` exactly; if a task is added or removed, update README.md accordingly. For data folder contents, point to `source_data/CONTENT.md` and `output_data/CONTENT.md` rather than duplicating their content inline.
